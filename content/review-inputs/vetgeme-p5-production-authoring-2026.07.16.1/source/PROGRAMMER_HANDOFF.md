# Задание программисту: подключить P5 production package

## Цель

Подключить содержимое `p5-production-authoring` к уже реализованным `resource-scheduler-v5` и `operations-runtime-v5`, не переписывая их без подтверждённой несовместимости. После интеграции персонал, помещения, оборудование, исследования и этапы визита должны занимать реальное время и ресурсы, сохраняться, восстанавливаться и безопасно обрабатывать перегрузку.

Это интеграционное задание, а не повтор вчерашних P5–P10: вчера был создан технический механизм и fail-closed gate, сейчас в него добавляются полные production-данные P5.

## Перед началом

1. Зафиксировать текущие `HEAD`, ветку, dirty-файлы и список уже подключённых P3/P4/P6/P7/medical изменений.
2. Сравнить схемы пакета с фактическими экспортами `systems/resource-scheduler-v5.js` и `systems/operations-runtime-v5.js`.
3. Не перезаписывать пользовательские `art/`, `handoff/`, medical authoring и текущие изменения другого чата.
4. Не менять save schema. Если текущего сохранённого P5-state объективно недостаточно, остановить интеграцию и оформить отдельный version+migration plan.

## P5-I1. Импорт и gate

- Добавить отдельный адаптер чтения P5-каталогов; не вшивать авторские данные в UI или renderer.
- Проверять `catalogVersion`, уникальность ID и полный набор обязательных файлов.
- До успешного завершения всех этапов оставить package gate выключенным.
- Не выключать существующий playable clinical baseline.
- Каталог ресурсов содержит потенциальные ресурсы, а не автоматически принадлежащие игроку.

Приёмка:

- повторный импорт идемпотентен;
- неизвестный ID завершается fail-closed;
- в save не попадают display title как идентификаторы;
- клинические тексты/результаты не создаются адаптером P5.

## P5-I2. Ресурсы и активация

- Импортировать 10 сотрудников, 12 помещений и 27 equipment-resources из `resource-catalog.json`.
- При старте новой кампании активировать только записи с `startsActive: true` и выполненными `activationRequirements`.
- Для сотрудников после unlock требовать найм и назначение смены.
- Для помещений после unlock требовать P6-владение, доставку и готовность.
- Для оборудования требовать P6-владение, доставку, обучение, актуальное обслуживание и запас обязательных расходников.
- Не использовать `capacityPerDay` как одновременную вместимость; брать `runtimeResourceTemplate.capacity`.

Приёмка:

- chapter unlock сам по себе ничего не дарит;
- один ресурс нельзя занять сверх capacity;
- проданное/сломанное/обслуживаемое оборудование немедленно перестаёт быть доступным новым задачам;
- reload сохраняет владение и активность без повторного создания ресурсов.

## P5-I3. Этапы визита и исследования

- Подключить 14 этапов из `visit-task-catalog.json`.
- Для выбора исследования P3 находить `usageId` в `investigation-usage-task-map.json`, затем базовую задачу в `research-task-catalog.json` и применять только `runtimeOverrides`.
- Не переносить в P5 клинический результат, правильный ответ или диагноз: они остаются в P3/medical presentation.
- Учитывать AND между группами и OR внутри `anyOf`.
- Не создавать отдельную бронь квалификации, если skill уже является capability выбранного staff-resource.

Приёмка:

- покрыты ровно 361 research ID и 1 864 usage ID;
- все 447 capability ID имеют execution mode;
- одна задача не занимает одного сотрудника дважды из-за skill-check;
- длительность изменяется усталостью только через сохранённые `percent` и `durationMultiplier`;
- fatigue не меняет диагноз, результат или правильность решения.

## P5-I4. Смены, делегирование и очередь

- Использовать `recommended-30-day-staffing.json` только как рекомендацию; фактический выбор врача игроком сохраняется отдельно.
- До приобретения второго кабинета одновременно работает один врач; после него разрешить ограниченное пересечение смен согласно policy.
- Делегировать только разрешённые capability по `operational-policies.json`.
- Диагноз, план, анестезия, review результата, urgent triage и стабилизация остаются doctor-only.
- Очередь сортируется текущим P5-ядром: priority, queuedAt, stable task ID.

Приёмка:

- выбор другого допустимого врача не сбрасывается после reload;
- отсутствие ассистента/администратора оставляет предусмотренный doctor fallback, но занимает время врача;
- запрещённая делегация отклоняется до постановки задачи.

## P5-I5. Handoff и сохранение

- Применять policy `not_allowed`, `midpoint`, `urgent_quarter_breakpoints`.
- Передавать в `handoffTask` только поля из `handoffRuntimeContract`.
- Не вкладывать в команду medical payload.
- После handoff сохранять новые резервации и историю команды; replay command ID должен быть идемпотентен.

Приёмка:

- handoff не оставляет перекрывающиеся старые резервации;
- неподходящий сотрудник или capability отклоняются;
- JSON save/reload даёт тот же state;
- reload не возвращает задачу прежнему сотруднику.

## P5-I6. P6/P7-связи и срочная перегрузка

- P6 остаётся единственным владельцем stock, assets и maintenance ledger.
- Maintenance передаётся в P5 точным half-open `unavailableWindow`; не хранить второй maintenance-state в P5.
- Отсутствия создаются только событием P7 или явным решением игрока об обучении.
- При срочной перегрузке выполнить порядок: основной квалифицированный ресурс → альтернативный → отдельная стабилизация → `safe_referral`.
- Срочную задачу нельзя молча удалить или завершить смену, пока она не выполнена, не передана или не отменена с явным safe route.

Приёмка:

- причина блокировки ядра — `urgent_capacity_unavailable_safe_route_required`;
- отмена urgent-задачи без `safeRouteId` отклоняется;
- после обслуживания/отсутствия ресурс возвращается ровно в `endAt`;
- renderer не может вернуть ресурс в эксплуатацию.

## P5-I7. UI без редизайна

Не менять утверждённую компоновку кабинетов. Добавить только необходимые состояния существующих элементов:

- кто выполняет задачу;
- помещение/оборудование;
- начало, ожидаемое завершение и причина ожидания;
- усталость и невозможность продлить смену;
- действие handoff;
- безопасное направление при срочной перегрузке.

Клинически необязательное исследование не скрывать: цена, время, доверие и отказ владельца должны давать последствия.

## Обязательные проверки

1. `node p5-production-authoring/scripts/build-p5-package.mjs`
2. `node p5-production-authoring/scripts/validate-p5-package.mjs`
3. `node scripts/test-resource-scheduler-v5.js`
4. `node scripts/playtest-p5-runtime.js`
5. синтаксические и content checks проекта;
6. browser smoke: обычный приём, urgent overcapacity, handoff, maintenance, absence, reload;
7. reset каждого режима и cancel без мутации;
8. `git diff --check`.

## Коммиты

Делать отдельные безопасные коммиты: adapter/gate, resources, tasks, P6/P7 bridges, UI states, tests. Не смешивать медицинское авторство с рефакторингом движка.

## Условие включения

Поменять runtime gate с `false` на `true` можно только после всех проверок выше. Отчёт должен перечислить изменённое поведение, проверки, намеренно не изменённые части, риски, ветку и коммиты.
