# Задание программисту: P9 visual-state `.2`

## Цель

Подключить визуальные проекции P5/P6/P7 к существующему экрану клиники без
редизайна композиции и без переноса симуляционной логики в renderer/DOM.

## Порядок

1. После P3–P7 `.2` и P5 `.2` провести P0-аудит текущего visual runtime и
   `art/ASSET_MANIFEST.json`.
2. Импортировать четыре generated-каталога пакета как review input.
3. Комната, оборудование и сотрудник получают visual state только из
   сериализуемого simulation state. Наличие sprite никогда не означает покупку,
   обучение или готовность.
4. Сохранить текущие зоны: верхний левый блок, правую очередь и нижний HUD.
   Центр игрового поля не перекрывать. Длинные тексты — drawer; на мобильном
   панели сворачиваются в chips.
5. Использовать DOM для человеческого текста, canvas — для комнаты, предметов,
   людей, животных и коротких state overlays.
6. Для отсутствующих sprites показать честную русскую подпись. Не выдавать
   случайный предмет за конкретное оборудование. Shared analyzer/procedure shell
   обязательно получает видимую подпись варианта.
7. Уведомления строить как «что случилось → что изменилось → что можно сделать».
   Не показывать raw ID и reasonCode игроку.

## Обязательные сценарии

- не куплено → заказано → доставка → подготовка/обучение → готово;
- обслуживание due/active и возврат в ready;
- stockout при видимом исправном приборе;
- помещение закрыто/строится/готово/занято;
- сотрудник нанят без смены, на смене, занят, отдыхает, отсутствует;
- save/reload visual parity каждого состояния;
- 1280×720, широкое окно, узкое окно и mobile collapse;
- reduced motion;
- скриншотная матрица без перекрытия центральной клиники.

## Границы

Не менять медицинские тексты, баланс, lifecycle, campaign evidence, save schema
или art-файлы. Если для состояния нужен новый art, оформить отдельный asset gap,
а не рисовать его в этом коммите.
