# Пояснение к архитектуре генератора и сохранениям

Статус: каноническое дополнение к [SCENARIO_GENERATOR_SPEC.md](SCENARIO_GENERATOR_SPEC.md). Краткая исполнимая версия находится в [CONTENT_GENERATOR.md](CONTENT_GENERATOR.md).

---

Я дал **общую архитектуру генератора**, но наполнил её медицинским контентом только для первой недели. То есть сам механизм должен работать всю игру, а 16 клинических шаблонов — это первый пакет данных для проверки механизма.

И важное уточнение:

> **При каждом запуске приложения пациенты не должны меняться. При каждой новой кампании — должны.**

Если игрок просто закрыл браузер и продолжил сохранение, его очередь, пациенты и запланированные повторные визиты обязаны остаться прежними. Иначе можно будет перезапускать игру до появления удобных случаев, а последствия решений будут исчезать.

# Как именно должна работать случайность

| Действие игрока | Что происходит |
|---|---|
| Запустил игру и создал новую кампанию | Создаётся новый случайный `campaignSeed`, первая неделя будет отличаться |
| Закрыл браузер и снова открыл сохранение | Возвращаются те же пациенты и то же расписание |
| Нажал «Планировать следующий день» | День генерируется один раз с учётом результатов предыдущего дня |
| Перезагрузил страницу после планирования | День остаётся тем же |
| Начал ещё одну новую кампанию | Получает другой seed и другую комбинацию случаев |
| Ввёл тот же seed вручную | Получает ту же кампанию — полезно для тестирования |
| Запустил режим разработчика | Может принудительно генерировать новые варианты |

То есть нужно различать:

- **запуск приложения**;
- **продолжение сохранения**;
- **начало новой кампании**;
- **генерацию следующего дня**.

Случайность привязана к новой кампании и планированию новых дней, а не к открытию страницы.

Если игрок закроет игру после второго пациента дня 3, после возвращения он увидит этих же пациентов.

# Не должен ли первый пациент всегда быть Акифом

Нет. Лучше зафиксировать не пациента, а **роль первого визита**.

Например:

> Первый визит должен быть простым, несрочным, доступным текущему оборудованию и обучать полному циклу приёма.

Но сам визит выбирается из безопасного набора:

- неосложнённый грибковый отит;
- ушной клещ;
- простая блошиная инвазия;
- лёгкая пищевая погрешность.

Имя, вид животного, внешний вид и владелец также меняются.

Возможный вариант:

```text
Обучающий слот 1
├── EAR-01: грибковый наружный отит
├── EAR-02: ушной клещ
├── SKIN-01: блошиная инвазия
└── GI-01: пищевая погрешность
```

Однако я бы сделал первую смену сбалансированной:

1. первый пациент — простая локальная проблема;
2. второй — другой тип осмотра;
3. третий — случай, где важен анамнез.

Тогда игрок не лечит три уха подряд.

## Первый запуск вообще

Для первого прохождения можно использовать более управляемое обучение:

- первый визит выбирается из двух максимально простых шаблонов;
- игра показывает подсказки;
- пациент не уходит из очереди;
- время приостанавливается.

После первого завершённого обучения новые кампании могут использовать более широкий случайный набор.

# Что именно является общей системой для всей игры

Генератор должен состоять из пяти уровней.

## 1. Режиссёр кампании

Он определяет:

- текущую главу;
- сложность;
- доступные заболевания;
- оснащение клиники;
- возможности персонала;
- сюжетные события;
- максимальную нагрузку;
- образовательную задачу этапа.

Он не выбирает конкретного Бакса или конкретную Ирину. Он говорит, например:

> Сегодня нужно 5 визитов, минимум 3 клинических семейства, один повторный пациент, один случай с противоречивым анамнезом, срочных случаев нет.

## 2. Планировщик дня

Он:

1. добавляет обязательные повторные визиты;
2. добавляет сюжетный или обучающий слот;
3. выбирает новые клинические шаблоны;
4. проверяет разнообразие;
5. рассчитывает общую нагрузку;
6. распределяет прибытия по времени;
7. создаёт цели дня;
8. сохраняет готовый день.

## 3. Сборщик конкретного визита

Он соединяет:

```text
клинический шаблон
+ вариант жалобы
+ пациент
+ владелец
+ модификаторы владельца
+ скрытые факты
+ темперамент животного
```

Например:

```text
Клинический шаблон:
EAR-02 — ушной клещ

Пациент:
Мурка, кошка, 2 года, робкая

Жалоба:
«Сильно чешет оба уха, внутри тёмная грязь»

Владелец:
спокойный, но невнимательный

Модификаторы:
несколько животных дома
считает, что у домашней кошки паразитов быть не может

Скрытый факт:
вторая кошка тоже начала чесать уши
```

## 4. Проверяющий модуль

Он отклоняет неправильную комбинацию, если:

- случай нельзя диагностировать имеющимся оборудованием;
- нет безопасного варианта направления;
- критический факт нельзя выяснить;
- назначена цель, для которой нет подходящего пациента;
- превышено количество срочных случаев;
- в день попали четыре одинаковых диагноза;
- два одинаковых владельца идут подряд;
- нагрузка превышает возможности смены.

## 5. Планировщик последствий

После приёма он создаёт будущие события:

- контрольный приём;
- звонок;
- результат исследования;
- возврат из-за ухудшения;
- возврат из-за неправильного выполнения назначения;
- благодарность;
- жалобу;
- отказ от повторного визита.

Именно поэтому правильнее генерировать не всю кампанию заранее, а каждый следующий день после окончания предыдущего.

---

# Нужно ли заранее генерировать всю первую неделю

Полностью — нет.

В начале недели можно создать только **скелет**:

```text
День 1 — базовый приём
День 2 — скрытая информация и повторный визит при наличии
День 3 — очередь и противоречивый анамнез
День 4 — срочный триаж
День 5 — смешанная проверка
```

Но конкретные пациенты создаются по дням.

Причина проста: в начале первого дня игра ещё не знает:

- кого игрок успешно принял;
- кому назначил контроль;
- кто выполнил лечение;
- кто ухудшился;
- кто ушёл;
- кому потребуется повторный визит;
- какой владелец потерял доверие.

Правильная последовательность:

```text
Создание кампании
→ генерация дня 1
→ сохранение дня 1
→ прохождение дня 1
→ расчёт последствий
→ генерация дня 2
→ сохранение дня 2
→ прохождение дня 2
...
```

---

# Что означает проверка на 10 000 недель

Это **не 10 000 реальных запусков игры игроками**.

Это автоматический тест разработчика, который работает без графики.

Программа делает примерно следующее:

```text
для seed 1:
    сгенерировать дни 1–5
    проверить ограничения

для seed 2:
    сгенерировать дни 1–5
    проверить ограничения

...

для seed 10000:
    сгенерировать дни 1–5
    проверить ограничения
```

То есть компьютер в памяти создаёт 10 000 условных кампаний и ищет ошибки.

Он не:

- открывает Chrome 10 000 раз;
- не рисует клинику;
- не создаёт настоящие пользовательские сохранения;
- не ждёт прохождения дней;
- не нажимает интерфейс вручную.

Такой тест может выполняться за секунды или минуты в зависимости от сложности генератора.

## Зачем нужно так много вариантов

Проблема случайных генераторов в том, что ошибка может встречаться редко.

Например:

- один раз на 700 недель появляется цель повторного визита без повторного пациента;
- один раз на 2 000 недель критический случай выдаётся без способа обнаружить ключевой факт;
- один раз на 5 000 недель генерируются три срочных пациента;
- иногда всё расписание состоит из ушей;
- определённый диагноз практически никогда не выбирается из-за неверного веса.

При ручной проверке такие ошибки можно не встретить вообще. Массовая генерация их обнаруживает.

---

# Что именно проверять в этих 10 000 тестовых кампаниях

## Обязательные проверки

В каждой неделе:

- пять дней успешно сгенерированы;
- ни один день не пуст;
- количество пациентов соответствует сложности;
- оборудование соответствует случаям;
- каждый критический факт можно обнаружить;
- срочных случаев не больше допустимого;
- цель дня соответствует составу пациентов;
- повторный визит связан с существующим пациентом;
- пациент сохраняет имя и владельца;
- один диагноз не повторяется подряд;
- общая нагрузка укладывается в предел;
- первый день всегда проходим;
- четвёртый день содержит подходящий триажный случай;
- перезагрузка с тем же seed даёт тот же результат.

## Проверки распределения

После всех 10 000 недель формируется отчёт:

```text
EAR-01 встретился: 7 842 раза
EAR-02 встретился: 7 105 раз
SKIN-01 встретился: 8 014 раз
GI-01 встретился: 7 961 раз
UR-02 встретился: 9 998 раз
...
```

Если один обычный случай встретился 20 000 раз, а другой только 40, значит веса настроены неправильно.

Также проверяется:

- среднее число ушных случаев;
- среднее число кожных;
- число срочных;
- количество повторных визитов;
- средняя нагрузка по дням;
- число конфликтных владельцев;
- число случаев с ограниченным бюджетом;
- число совпадающих недель.

---

# Как проверять, что новые кампании действительно отличаются

Для недели нужно формировать **структурный отпечаток**.

Не стоит включать туда имя и цвет животного, потому что тогда любая неделя будет формально уникальна только за счёт косметики.

Структурный отпечаток может выглядеть так:

```text
D1:
EAR-02 + calm + multi-pet
SKIN-01 + anxious
GI-01 + inattentive

D2:
FOLLOWUP-EAR-02
GI-03 + hurried
SKIN-02 + internet-diagnosis
EAR-03 + self-treatment
```

Из этого создаётся строка или hash.

Затем сравниваются 1 000–10 000 кампаний.

Разумные критерии:

- один и тот же seed всегда даёт полностью одинаковую неделю;
- два последовательных случайных seed отличаются минимум двумя случаями первого дня;
- у соседних кампаний не совпадает больше 60–70% структуры первой недели;
- точные структурные дубликаты встречаются редко;
- один и тот же точный сценарий не повторяется внутри кампании без причины;
- косметические отличия не считаются полноценным разнообразием.

## Защита от слишком похожей новой кампании

Можно хранить отпечатки последних нескольких начатых кампаний на устройстве.

При создании новой кампании:

```text
1. Создать новый seed.
2. Сгенерировать предварительную первую неделю.
3. Сравнить с последними неделями игрока.
4. Если совпадение слишком высокое — создать другой seed.
5. Повторить максимум 10–20 раз.
```

Это не обязательно для первого прототипа, но полезно позднее.

# Как выглядит тестовый интерфейс разработчика

В режиме разработчика стоит сделать отдельное окно:

```text
ГЕНЕРАТОР КАМПАНИИ

Seed: MECHEVET-A7K2-19
Версия генератора: 3

[Сгенерировать день]
[Сгенерировать неделю]
[Сгенерировать 100 недель]
[Сгенерировать 10 000 недель]

Проверки:
✓ Все дни созданы
✓ Оборудование доступно
✓ Цели соответствуют пациентам
✓ Срочных случаев не больше 1
✓ Критические факты обнаружимы
✓ Повторные визиты корректны

Разнообразие:
Уникальных структур: 9 742 / 10 000
Среднее совпадение недель: 31%
Максимальное совпадение: 68%

Ошибок: 0
```

Для каждой ошибки сохраняется seed:

```text
Ошибка:
Повторная цель без повторного визита

Seed:
TEST-4832

День:
2
```

После этого разработчик вводит `TEST-4832` и получает точно такой же проблемный день в игре.

# Как сохранить всё это в сохранении

Минимально:

```ts
interface CampaignSave {
  saveVersion: number;
  generatorVersion: number;

  campaignId: string;
  campaignSeed: string;

  currentDay: number;
  difficulty: Difficulty;

  generatedDays: Record<number, GeneratedDay>;

  pendingFollowUps: PendingFollowUp[];

  seenCaseCounts: Record<string, number>;
  recentCaseIds: string[];
  recentScenarioFingerprints: string[];

  clinic: ClinicState;
  staff: StaffState[];
  patients: PatientHistory[];
}
```

Критически важно поле:

```ts
generatedDays
```

Если день уже создан, игра загружает его отсюда и больше не обращается к генератору.

Правило:

```ts
function getOrGenerateDay(dayNumber: number): GeneratedDay {
  const savedDay = save.generatedDays[dayNumber];

  if (savedDay) {
    return savedDay;
  }

  const newDay = generateDay(save, dayNumber);

  save.generatedDays[dayNumber] = newDay;
  saveImmediately();

  return newDay;
}
```

Сохранение должно происходить сразу после генерации, а не в конце дня.

# Общие правила генератора для всех будущих недель

В дальнейшем не нужно переписывать механизм. Добавляются новые данные.

## У клинического шаблона должны быть условия открытия

```ts
unlock: {
  minimumCampaignDay: 8,
  requiredClinicLevel: 2,
  requiredEquipment: ["urine-analyzer"],
  requiredSkills: ["basic-laboratory"],
  requiresSeenCases: ["UR-01"]
}
```

## Должны быть правила частоты

```ts
generation: {
  baseWeight: 5,
  cooldownVisits: 8,
  maximumPerDay: 1,
  maximumPerWeek: 2,
  workload: 1.5,
  severity: "priority"
}
```

## Должна быть совместимость

```ts
compatibility: {
  allowedSpecies: ["cat"],
  allowedSex: ["male"],
  allowedOwnerProfiles: ["anxious", "calm", "inattentive"],
  forbiddenOwnerModifiers: ["extremely-low-observation"]
}
```

## Должны быть медицинские гарантии

```ts
safety: {
  criticalFacts: ["urine-absent"],
  discoveryPaths: [
    "ask-last-normal-urination",
    "ask-urine-volume",
    "physical-bladder-exam"
  ],
  minimumSafeActions: [
    "urgent-referral",
    "emergency-stabilization"
  ]
}
```

По этой модели затем можно добавить:

- вторую неделю;
- лабораторные заболевания;
- хронические случаи;
- травмы;
- рентген;
- УЗИ;
- стоматологию;
- стационар;
- поздние тяжёлые решения.

---

# Какое решение я рекомендую зафиксировать

1. **Общая система генерации проектируется сразу для всей игры.**
2. **Медицинскими данными пока полностью заполняется только первая неделя.**
3. **Каждая новая кампания получает новый случайный seed.**
4. **Продолжение существующей кампании ничего не перегенерирует.**
5. **Каждый следующий день создаётся один раз после предыдущего дня.**
6. **Повторные пациенты берутся из реальных последствий, а не из случайного списка.**
7. **Первый визит имеет фиксированную обучающую функцию, но не фиксированного Акифа.**
8. **10 000 недель создаются только автоматическим тестом разработчика.**
9. **Одинаковый seed позволяет точно воспроизвести любую ошибку.**
10. **День немедленно сохраняется после генерации.**

Таким образом, игрок получает новую комбинацию первой недели при каждой **новой кампании**, но не может менять очередь простым перезапуском браузера. Это одновременно даёт разнообразие, устойчивое сохранение, проверяемость и нормальные причинно-следственные связи.
