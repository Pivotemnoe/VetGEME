# Задание Codex: заменить заглушки Tier 01 точным контентом и подключить его безопасно

## Источник истины

Используй файлы этого архива **дословно**. Медицинские жалобы, вопросы, ответы владельцев, результаты осмотра, результаты исследований, предварительные диагнозы, объяснения и планы уже написаны.

**Запрещено:**

- придумывать новые медицинские формулировки;
- перефразировать утверждённые строки «для красоты»;
- генерировать ответы по шаблону во время выполнения игры;
- заменять «грибковый отит» на другую терминологию;
- добавлять кроликов в первый тир;
- восстанавливать удалённые заглушки;
- менять истинную медицинскую логику на основании имени пациента или владельца.

## Сначала зафиксировать исходное состояние

1. Создай отдельную ветку или резервный коммит.
2. Выполни текущие команды проекта и запиши результат:
   - typecheck;
   - unit tests;
   - текущая валидация контента;
   - текущий smoke test генератора;
   - production build.
3. Если исходная версия уже не проходит проверки, не маскируй ошибку новым контентом; сначала сообщи, что именно не проходит.

## Фаза 1. Подключить файлы как новый пакет

1. Не удаляй старый пакет сразу.
2. Подключи этот пакет под идентификатором `tier-01-v2` или аналогичным feature flag.
3. По умолчанию в production оставь текущий пакет, пока v2 не прошёл проверки.
4. Новый загрузчик должен читать строки из JSON без генерации или перефразирования.
5. Не менять `campaignSeed` при загрузке сохранения.
6. Один уже сгенерированный день должен храниться в сохранении целиком и не меняться после перезагрузки.

## Фаза 2. Сохранить принцип seeded-генератора

Новый пакет не является линейной кампанией с фиксированными пациентами.

Сохранить правила:

- новая кампания получает новый `campaignSeed`;
- одинаковые `campaignSeed + generatorVersion` дают одинаковый результат;
- день генерируется один раз;
- дневной план задаёт ограничения, а не фиксированный список;
- диагноз и медицинские тексты выбираются только из утверждённых JSON;
- имя, внешность, пол, допустимый возраст, профиль владельца и совместимые модификаторы выбираются генератором;
- повторный визит создаётся только из истории реально принятого пациента;
- если повторного пациента нет, применяется `fallbackRules` дня;
- незапланированный пациент не существует в предварительном расписании и создаётся после открытия клиники;
- `urgentSubset` входит в общее число визитов и не прибавляется второй раз.

## Фаза 3. Источники информации

В интерфейсе строго разделять:

- `initial_complaint` — первоначальная жалоба;
- `owner_history` — ответы владельца;
- `physical_exam` — объективный осмотр;
- `diagnostic_test` — исследование;
- `doctor_interpretation` — предварительный диагноз и план;
- `follow_up` — отложенный результат.

Анамнез не должен открывать результаты осмотра. Осмотр не должен автоматически показывать истинный диагноз.

## Фаза 4. Вопросы и домашние действия

1. Показывай только вопросы из `historyQuestions` конкретного клинического шаблона.
2. Выбирай точный ответ из `answers` по профилю владельца.
3. Для вопроса с `allowsHiddenHomeTreatment` выбирай строку только из `home-treatment-actions.json` и только из перечисленных `homeActionIds`.
4. Не прикрепляй домашнее лечение к каждому вопросу.
5. Поле `revealsFactIds` должно открывать только указанные факты.
6. Критический факт обязан иметь реально доступный путь из `discoveryPaths`.

## Фаза 5. Первый приём

Реализуй `FIRST_VISIT_GUIDED` из `tutorial-texts.json`:

- случай выбирается seeded-случайно из `eligibleCaseIds`;
- имя пациента и владелец меняются между новыми кампаниями;
- время приостановлено;
- раздражение и уход пациента отключены;
- ускорение отключено;
- на каждом шаге активны только `enabledActions`;
- остальные действия заблокированы;
- нужная кнопка пульсирует и отмечена стрелкой;
- переход выполняется только по `completeWhen`;
- чтение текста не расходует игровое время.

## Фаза 6. Экран планирования

До открытия клиники показывать только записанные визиты:

- время;
- имя;
- вид животного;
- короткую причину записи;
- отметку «повторный».

Не показывать:

- истинный диагноз;
- подробный анамнез;
- владельческий профиль;
- точную сущность незапланированного пациента.

Для walk-in выводить только: `Возможны незапланированные обращения: 0–1`.

## Фаза 7. Валидация

Добавь команду:

```bash
npm run validate:tier-01-v2
```

Она должна использовать `scripts/validate-tier-01-content-v2.mjs`.

После интеграции дополнительно проверить:

- загрузчик не изменяет строки;
- ни одна строка-заглушка не возвращена;
- нет вида `rabbit`;
- вопросы соответствуют клиническому шаблону;
- цели дня выбираются только при наличии совместимого визита;
- отсутствие реального follow-up не ломает день;
- незапланированный пациент создаётся после открытия;
- первый учебный приём блокирует неправильные кнопки;
- reload не меняет день;
- новый seed меняет состав новой кампании;
- старое сохранение продолжает открываться через старый пакет или корректную миграцию.

## Массовая проверка генератора

После подключения создай или адаптируй тест, который без графики генерирует 10 000 семидневных кампаний.

Это не 10 000 запусков браузера. Тест должен проверять данные в памяти:

- нет пустых дней;
- число визитов соответствует формуле;
- urgent не считается дважды;
- нет обязательного повторного визита без реального пациента или fallback;
- один и тот же seed воспроизводим;
- разные seed дают различия не только в именах;
- нет неподдерживаемого оборудования;
- все criticalFacts доступны;
- нет более одного тяжёлого конфликтного владельца в ранние дни;
- ни одно заболевание не доминирует из-за неправильных весов.

При ошибке сохранить seed и JSON дня.

## Что не делать

- Не переписывать всю архитектуру приложения.
- Не менять Canvas-сцену без необходимости.
- Не добавлять backend.
- Не менять экономику и цены в этой задаче.
- Не добавлять новые диагнозы.
- Не включать v2 по умолчанию, если тесты не проходят.
